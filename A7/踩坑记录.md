# A7 过程间常量传播踩坑记录

日期：2026-10-25。

写 A7 时，需要把指针分析、常量传播和求解器的分工理清楚。这里记录字段和数组读写中容易混淆的地方，以及对应的实现思路。

`InterConstantPropagation` 使用已经完成的指针分析结果判断别名，自己计算整数值；`InterSolver` 管理节点 fact 和 worklist。指针分析可以复用 A6，不需要在常量传播里重新实现。

## 1. load 和 store 容易写错的地方

| 容易写错的地方 | 为什么会错 | 应当怎么写 |
| --- | --- | --- |
| 特殊 load 只执行 `out.update(lhs, value)` 后返回，或者处理完后又调用普通 `cp.transferNode()` | 前一种写法没有把 IN 中其他局部变量传到 OUT；后一种写法会将已算出的 load 结果覆盖为 NAC | 从 `in.copy()` 构造完整候选 OUT，再覆盖 load 左值；特殊 load 自行返回，只有普通语句使用 `cp.transferNode()` |
| 使用 load 左值在 IN 中的旧值作为 meet 起点 | 例如旧 `x=100`、字段值为 3，赋值结果会被错误地合并成 NAC | 所有字段、数组 load 都从 UNDEF 开始汇总 store 写入值，不合并左值的旧值 |
| 从当前 load 的 IN 查询另一条 store 的右值 | store 和 load 之间变量可能已被重新赋值；跨方法时当前 IN 通常没有 store 的局部变量 | 通过 `solver.getInFact(store)` 获取 store 自己的 IN，再读取其右值 |
| 数组用 `Var.equals()` 比较索引，或将 store 索引与正在汇总的元素值比较 | 两个不同变量即使都等于 1 也会漏匹配；索引和元素值也被混淆 | 分别读取 `IN[load][i]`、`IN[store][j]`，按课程的 UNDEF/常量/NAC 规则判断 |
| 同 base 与别名 base 分两条路径处理 | 存在重复计算，且相同 base、不同索引变量但索引值相等的情况可能被漏掉 | 使用按抽象数组对象建立的 Map 收集候选 store，用 Set 去重，再统一比较索引 |
| 静态字段分支只取得 `JField` | 未真正计算静态字段读取结果 | 按 `JField` 从 `staticStores` 查询，汇总每条 store 的写入值 |
| store 的变化只沿 ICFG 后继传播 | 相关 load 可能在其他方法或出现在 store 之前，不能保证被重新计算 | 初始化时建立 `dependentLoads`；store 的 OUT 变化后，将候选 load 重新加入 solver 的 worklist |
| 只实现 transfer，没有完成求解器和配套 API | 没有节点事实和迭代流程，load 也无法查询其他 store 的值 | 求解器初始化全部节点，完成边传递、meet、节点传递和后继调度，并提供 `getInFact()`、`addWorkList()` |
| 特殊处理没有限制值类型 | 引用类型字段/数组 load 可能误入整数常量传播逻辑 | 在特殊 load 的传播入口使用 `ConstantPropagation.canHoldInt()`；引用关系仍由 PTA 提供。CPFact 不记录引用变量，调用和返回时读取它们得到 UNDEF，无需重复筛选 |
| 只复制键或根据中间修改判断 changed | `copyFrom()` 不删除目标中的多余键；中间变化可能使循环无谓重复入队 | 比较最终候选 OUT 与旧 OUT，只有不同才 `clear()` 后复制，并返回 true |

## 2. store 为什么要按 Map 分组

这些结构保存在 `InterConstantPropagation` 中，声明字段时创建。这里按一次分析创建一个实例使用，`initialize()` 负责填充，不额外处理重复初始化。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `storeArraysStmt` | `Map<Obj, Set<StoreArray>>` | 一个抽象数组对象可能被哪些 store 写入；同一 store 可以属于多个对象 |
| `instanceStores` | `Map<JField, Set<StoreField>>` | 写入同一实例字段声明的候选 store；查询时还要检查两个 base 的 points-to set 是否有交集 |
| `staticStores` | `Map<JField, Set<StoreField>>` | 写入同一静态字段的 store，无需 base 别名判断 |
| `dependentLoads` | `Map<Stmt, Set<Stmt>>` | 每条 store 变化后，需要重新调度哪些 load |

数组候选只根据 base 的指针集合建立。不能在初始化阶段用索引的常量值过滤依赖，因为常量传播还没有启动，索引之后可能从 UNDEF 变成常量或 NAC。

初始化只收集候选和依赖，不重复筛选值类型；真正计算 load 时才判断是否属于整型分析范围。

另外，`pta.getArrayIndexes()` 返回的是数组元素的抽象指针 `o[*]`，不是下标变量或具体下标。判断 `a[i]` 和 `b[j]` 是否可能访问同一位置，需要比较 base 的指针集和两个索引的抽象值，不能直接拿 `ArrayIndex` 与 base 的指针集比较。

## 3. load 如何计算值

对于数组：

```text
L: x = a[i]
S: b[j] = y
```

先根据 PTA 判断 a、b 是否可能指向同一个数组，再比较两个语句各自的索引值。匹配时，将 `IN[S][y]` 合并到 L 的结果中。

| `IN[L][i]` 和 `IN[S][j]` | 是否可能访问同一个元素 |
| --- | --- |
| 任意一个为 UNDEF | 否 |
| 两个都为常量 | 当且仅当常量相等 |
| 都不是 UNDEF，且至少一个为 NAC | 是 |

对于实例字段，要求同一个 `JField` 且 base 指针集有交集；对于静态字段，仅匹配同一个 `JField`。所有 load 都从 UNDEF 开始 meet，随后用结果覆盖左值，保留 IN 中其余局部变量。

例如 `v=7; a.f=v; v=8; x=a.f;` 中，应读取 store 时的 `v=7`，而不是 load 时的 `v=8`。若读到多个不同常量，结果为 NAC。

字段和数组的读写在这里按流不敏感处理：后出现的 store 也参与相关 load 的汇总；按照作业假设，不额外合并 Java 默认初始化值 0。

## 4. 为什么分析类也要调用 solver

solver 调用分析类的 transfer 来计算节点结果，分析类也可以调用 solver 查询其他节点的 fact、请求重新调度。这两个方向的调用并不冲突，迭代过程仍由 solver 控制。

1. 分析类的 `initialize()` 使用已经完成的 PTA 结果建立候选和依赖。此时 solver 尚未创建，不查询节点 fact。
2. solver 为 ICFG 全部节点分配独立的 IN/OUT，并将所有节点加入去重 worklist。只有程序入口方法的入口节点取得 boundary fact，普通被调方法的参数由 call edge 提供。
3. 处理一个节点时，先对每条入边的源 OUT 执行 edge transfer，再 meet 到该节点 IN，最后执行节点 transfer。
4. load 通过 `solver.getInFact(store)` 查询写入值；数组索引也在各自语句的 IN 中查询。
5. 节点 OUT 变化时，solver 调度 ICFG 后继；若该节点是存在依赖的 store，分析类额外调用 `solver.addWorkList(load)`。

入口的 boundary fact 需要在迭代中保留。如果入口节点也执行 transfer，只设置一次 OUT 可能会被入口的空 IN 覆盖，不能只考虑初始化时的值。A7 这里做的是前向数据流分析。

## 5. 测试时要检查哪些情况

在 `A7/tai-e` 目录运行：

```powershell
.\gradlew.bat test --offline --no-daemon
```

当前版本结果：**9 个测试通过，0 失败、0 错误、0 跳过；OJ 评测全部通过**。

- `InterCPAliasTest`：9 个仓库用例，覆盖字段、静态字段、多 store、数组、循环、跨方法和对象敏感精度，与 expected 文件比较。

下面 6 类场景也曾通过额外回归测试验证。当前仅保留仓库测试，这些检查点留作复习：

| 检查点 | 预期结果 |
| --- | --- |
| 字段 store 后右值变量被重新赋值，load 前左值有旧值，且其他局部变量后续参与运算 | `result=7`，`sum=16` |
| 数组的不同索引变量具有相同值，store 后索引和右值均被重新赋值，同时检查相同 base 和别名 base | `answer=7`，`sameBase=7`，`distinct=8`，`sum=13` |
| void 写入方法与独立读取方法之间传播实例字段、数组和静态字段值 | 分别为 41、43、47 |
| load 之后出现不同值的 store | 先前 load 最终为 NAC |
| 引用字段和引用数组读取，同时通过这些引用继续读取整型字段 | 引用变量不记录在整数 fact 中，后续整型读取为 11 |
| NAC 和 UNDEF 数组索引 | 未知索引写入不同值时为 NAC；所有候选值均为 11 时读取为 11；UNDEF 索引不贡献写入，UNDEF 索引读取为 UNDEF |

当时的额外测试类 `InterCPAliasRegressionTest` 和输入 `AliasRegression.java` 已移除。UNDEF 索引场景使用除零表达式产生课程格中的 UNDEF；测试只运行静态分析，不执行该输入程序。

本地测试和 OJ 都通过后，仍要理解这些场景为什么得到对应结果，不能只以通过测试代替对传播规则的理解。
