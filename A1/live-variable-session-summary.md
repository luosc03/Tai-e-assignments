## Fact 类型

- A1 中每个 `Stmt` 节点关联的 `IN fact` 和 `OUT fact` 的具体类型是 `SetFact<Var>`。
- 在 `Solver<Node, Fact>` 或 `DataflowAnalysis<Node, Fact>` 中，`Fact` 只是泛型占位符；在 A1 中实际对应 `SetFact<Var>`。
- `LiveVariableAnalysis` 中参数类型已经明确为 `SetFact<Var>`，可以直接使用 `add`、`union` 等方法。
- 泛型 `Solver<Node, Fact>` 不应直接调用 `SetFact` 的方法，因为编译器不能假设 `Fact` 一定是 `SetFact<Var>`。应通过 `analysis` 提供的接口（如 `meetInto`、`transferNode`）操作 fact。

## `LValue`、`RValue` 与 `Var`

- `Var` 同时实现了 `LValue` 和 `RValue`。
- `stmt.getUses()` 返回 `List<RValue>`，其中不一定每个元素都是 `Var`，因此不能把整个列表直接强转成变量集合。
- 处理单个 use 时应先判断它是否为 `Var`，再转为 `Var`；不能写 `Fact instanceof SetFact<Var>`。
- `instanceof` 的左侧必须是变量，例如 `fact instanceof SetFact<?>`；而 `SetFact<Var>` 不能直接用于 `instanceof`，这是泛型擦除导致的。

## 后向活跃变量分析的关键关系

```text
OUT[B] = 所有后继节点 IN 的并集
IN[B]  = USE[B] ∪ (OUT[B] - DEF[B])
```

- 出口节点的边界事实是 `OUT[exit] = ∅`。
- 非边界节点通常从空集开始，因为活跃变量集合使用并集，空集是最小事实；迭代过程中信息逐渐增加。
- `IN` 和 `OUT` 不能互相替代：后向 transfer 的方向是 `OUT → IN`，而 `IN` 会沿控制流反向影响前驱节点的 `OUT`。
- `newInitialFact()` 表示非边界节点的初始 fact，不是只给 `IN` 使用；在 Tai-e A1 的设计中，节点的 `OUT` 也需要对应的初始 fact。

## 迭代停止条件的澄清

- 如果使用 worklist，或在处理当前节点后立即把其 `IN` 传播到前驱的 `OUT`，那么可以根据传播后目标 `OUT` 是否变化来决定是否继续处理：没变表示没有新信息，变了则可能需要更新前驱。
- 如果是普通整轮扫描，只检查本轮各节点自己的 `OUT` 是否变化，则依赖遍历顺序。若先处理前驱、后处理后继，后继本轮才更新的 `IN` 可能来不及影响前驱的 `OUT`，可能需要下一轮。
- 因此，“检查 `OUT` 是否变化”不是绝对错误，但必须结合传播方式和遍历顺序；检查后向 transfer 产生的 `IN` 变化通常更直接、稳妥。

## 遍历顺序为何不影响最终结果：理论推导

### 1. 把活跃变量分析写成数据流方程

设：

- `V` 是当前方法中所有变量的有限集合；
- `USE[B]` 是语句 `B` 使用的变量集合；
- `DEF[B]` 是语句 `B` 定义的变量集合；
- `Succ(B)` 是 `B` 的后继节点集合。

对每个节点 `B`，活跃变量分析的方程是：

```text
OUT[B] = ⋃ IN[S]       (S ∈ Succ(B))
IN[B]  = USE[B] ∪ (OUT[B] - DEF[B])
```

出口节点没有后继，因此边界条件为：

```text
OUT[exit] = ∅
```

定义节点 `B` 的 transfer 函数：

```text
f_B(X) = USE[B] ∪ (X - DEF[B])
```

于是，`OUT` 由后继节点的 `IN` 经过 meet（集合并）得到，`IN` 再由 `f_B` 得到。

### 2. 为什么可以保证迭代收敛

每个节点的 fact 都是 `V` 的子集，因此事实所在的格是：

```text
(P(V), ⊆)
```

其中 `P(V)` 是 `V` 的幂集，底元是 `∅`。在这里采用的子集偏序下，集合并是 join（最小上界）；Tai-e 的 API 将执行这种合并的接口命名为 `meetInto`，这是框架层面的命名。若采用活跃变量分析中常见的反向偏序，集合并也可以对应为 meet。无论采用哪种术语约定，关键性质都是并集操作单调，且从 `∅` 开始迭代。因为 `V` 有限，这个格也是有限的。

`f_B` 是单调函数。若 `X ⊆ Y`，则：

```text
X - DEF[B] ⊆ Y - DEF[B]
USE[B] ∪ (X - DEF[B]) ⊆ USE[B] ∪ (Y - DEF[B])
```

所以：

```text
X ⊆ Y  ⇒  f_B(X) ⊆ f_B(Y)
```

节点间的并集传播同样是单调的。整个 CFG 上的方程系统因此构成一个单调数据流框架。

从所有 fact 都为 `∅` 开始，每次迭代只会增加信息，不会超过 `V`。每个节点的每个变量最多被加入一次，所以经过有限次变化后必然达到不动点：

```text
X* = F(X*)
```

这里的 `X*` 是从底元开始迭代得到的最小不动点，也就是满足这些数据流方程的最小解。

### 3. 为什么正向和反向遍历都能得到同一个结果

考虑一条简单路径：

```text
A → B → C
```

后向分析中，`A` 依赖 `B` 的 `IN`，`B` 又依赖 `C` 的 `IN`。

- 反向遍历 `C, B, A`：依赖节点先处理，信息可以在同一轮中向前传播较远的距离。
- 正向遍历 `A, B, C`：处理 `A` 时可能只能看到上一轮的 `IN[B]`，但 `B` 和 `C` 更新后，下一轮会再次处理 `A`。

因此，遍历顺序只改变每轮能传播多远以及需要多少轮，不改变最终不动点。只要每轮都处理所有节点，并且持续迭代到没有事实变化，正向和反向顺序都属于公平的迭代顺序，最终都会满足同一组方程。

反向顺序通常更高效，是因为它更符合后向方程的依赖方向；这属于收敛速度的优化，而不是正确性的必要条件。若只扫描一轮就停止，或者不满足单调性、有限格和持续迭代等条件，遍历顺序才可能影响结果。
